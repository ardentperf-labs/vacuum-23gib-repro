# 23 GiB Standard HDD: receiver disconnect and control

The archive-enabled pair reproduced more than two hours with all ten treatment writers stalled while the control continued. See [REPORT.md](REPORT.md) and [DIAGNOSIS.md](DIAGNOSIS.md). Both original harness runs remain marked incomplete: a marker parsing bug triggered early client shutdown, and cleanup lost the treatment final native transaction logs. Recovered evidence supports the long-stall result but leaves the exact first resumed write and final treatment latency distribution unknown.

Two isolated East US stacks restore the same retained, verified, offline CNPG DATA/WAL snapshot pair. Each uses two Standard_D2s_v4 workers, PostgreSQL 16.15, CNPG 1.30.1, and separate 512 GiB Standard_LRS DATA and WAL disks on both primary and replica. Azure host caching is disabled. The original PostgreSQL settings and preferred synchronous ANY 1 replica configuration are retained. Both lanes use the same pinned PostgreSQL 16.15 system image, which includes the Barman Cloud tools needed for the verified archive path.

Both run VACUUM (VERBOSE, FREEZE) on the existing 23 GiB fixture and a tiny logged pgbench client: 5 TPS total, ten persistent connections, synchronous_commit=on, no latency limit or statement timeout. A five-minute healthy warm-up precedes VACUUM. The planned completion criterion was at least 140 minutes from VACUUM start, VACUUM completion, replay catch-up, and a healthy client tail. The harness bug prevented that final client-tail criterion; the recovered analysis preserves this distinction.

The treatment sends one SIGTERM to the verified replica walreceiver at the actual remote SQL VACUUM start marker plus 600 seconds. The runner confirms one recovery-mode walreceiver in SQL, checks the matching Linux process PID, start time, UID, executable and command line, rechecks SQL and process identity, then sends `kill -TERM` to that PID. The control records the corresponding point without sending a signal. SIGTERM reproduces a receiver disconnect; the primary sender-timeout code path is a distinct trigger. Outcome claims follow the measurements.

Configured collectors capture primary/replica DATA/WAL reads/writes, linear-axis await/IOPS/throughput graphs, client native completion logs and latency (final treatment logs were lost; control logs were recovered), one-second session waits/ages/blockers, VACUUM progress, replication LSNs/senders/receiver, synchronous configuration, WAL/checkpoint counters, pg_stat_io and pg_stat_recovery_prefetch, Linux block/controller/queue/CPU/memory/pressure samples, and diagnostic BCC latency histograms. Azure captures exact disk and exact VM/per-LUN metrics at native one-minute grain, metric definitions, raw responses and missing-point evidence. CNPG operator logs and a Cluster watch record management changes.

Both VACUUMs finished. Recovery separately downloads and checksums evidence before deleting only verified owned snapshot-free test resources. The shared retained pair and its required local recovery metadata remain preserved. Protected source disks are copied through the caller’s Azure identity, then statically bound to the owned primary DATA/WAL claims. Source snapshots, locks and source permissions are left intact. No Git staging, commit or push is authorized.

Private runtime source metadata and kubeconfigs live outside the GitHub checkout. The published source preparation script requires locally supplied shared/source-pair.json, source-pair-proof.json, source-backup-status.json and source-restore-audit.json; these bind the exact private snapshot restore set and should not be copied from another subscription blindly. In the private experiment workspace, provision each stack, then run run-controller.py. Reviewed anonymized results are copied into the local GitHub checkout after measurement. Large raw text datasets may be gzip-compressed without changing their measurements; decompress them before using analysis helpers that expect the original filenames.

Working Azure Blob WAL archiving is a required preparation gate. Each stack gets an owned Standard_LRS private storage account and isolated container/prefix. CNPG’s `spec.backup.barmanObjectStore` remains configured throughout measurement. Before starting VACUUM, the archive smoke closes a known primary WAL segment, downloads its Blob independently, then restores that segment through the replica’s CNPG manager into a temporary file outside PGDATA. All three byte counts and hashes must match. The verified smoke WAL and required recovery metadata remain local. The user stopped the optional full post-test archive download; it is not needed to restore the retained offline snapshot pair. The temporary archive account is removed after the diagnostic evidence is collected.

The signal/control actions run once on a separate monotonic scheduler derived from the actual VACUUM marker. They record the remote action time and dispatch lateness, so a slow metric sample cannot silently delay SIGTERM. After measurement, archived-WAL restore logs are related to sender/receiver state and client completions. Successful `pg_stat_archiver` counters alone are insufficient proof of cloud upload; native successful restore events after SIGTERM are required to establish the intended recovery path.

The earlier [pilot](../experiments-20261012-walreceiver-sigterm/DIAGNOSIS.md) had no object-store backend and a late signal. It was stopped at the user’s request and is explicitly invalid for the archive-recovery hypothesis. This corrected pair includes the client, uncached D2s_v4 HDDs, disk/VM/Azure metrics, and verified archive configuration in both lanes.

Before cleanup, the read-only recovery capture also retains timeline history, pg_control, pg_controldata, recovery labels and available stable WAL locally. Private file hashes and a public recovery manifest are verified by teardown; these files cover recovery metadata that may predate the newly configured Blob archive.
