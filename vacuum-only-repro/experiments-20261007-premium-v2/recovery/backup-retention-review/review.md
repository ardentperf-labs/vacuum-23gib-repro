# Paired CNPG backup retention review

Reviewed 2026-10-06 from the saved baseline Kubernetes/Azure evidence and official CloudNativePG/PostgreSQL documentation. The read-only live Deployment query identifies the installed operator as CloudNativePG 1.30.1. No restore, database change, storage change, or deletion was performed.

## Finding

**Yes: keep the stack's WAL archive if these online paired snapshots must remain reliably restorable after their Blob accounts are deleted.** The snapshots are paired, but the archive contains WAL needed to complete an online snapshot recovery. The matching `PGWAL` snapshot is also mandatory because WAL uses a separate PVC; it does not replace WAL archived after that snapshot was taken.

The evidence is unusually direct: the Backup ran from `18:08:37Z` until `19:03:21Z`, but its DATA and WAL Azure snapshots were created at `18:08:48.204739Z` and `18:08:48.607019Z`. They therefore captured the two PVCs near the start of the online backup, about 54 minutes before PostgreSQL wrote the backup-stop record. Backup status names `000000010000004E00000050` as both the begin and end WAL segment. The successful Backup has `waitForArchive=true`, so completion depended on that required segment being archived. This is consistent with CloudNativePG's current recovery guidance that volume-snapshot recovery needs an external WAL archive to reapply changes and finalize recovery, and PostgreSQL's `pg_backup_stop(wait_for_archive)` contract that without the WAL required for consistency an online backup may be unusable.

For a future restore from this Backup, preserve the complete archived segment `000000010000004E00000050` and its PostgreSQL backup-history file. Because begin/end WAL are in the same segment, those are the minimum WAL archive items indicated for this backup itself; a target after the backup endpoint additionally needs every intervening WAL segment through that target. Do not treat the WAL snapshot as covering the backup-stop records merely because it is the matching snapshot. For the future recovery manifest, reference both `storage` and `walStorage` snapshots from the same Backup and configure the external archive source.

The decoded backup label identifies timeline 1 and the same start WAL segment. The Backup status names two outputs: `vacuum-backup-4b116309` (`PG_DATA`) and `vacuum-backup-4b116309-wal` (`PG_WAL`).

This is consistent with the archive being available during online snapshot seeding, but it is not a restore test with the Blob account removed.

## Minimal preservation if future use requires WAL replay

The baseline's minimum online-backup WAL set has been exported. Keep its local archive and receipt with the retained snapshots, and ensure this local evidence survives test resource-group cleanup. For future point-in-time recovery beyond the end of this Backup, preserve the continuous timeline-1 sequence through the chosen target as well. Keep an inventory with non-secret object names, byte sizes, SHA-256 checksums, archive prefix/server name, timeline, and first/last segment. Do not include storage keys, connection strings, Kubernetes Secret data, or credentials in that manifest. WAL contains database contents, so protect the exported bytes as database data.

Keep these already captured, non-secret records with the retained snapshots: `.state/prepare.json`, `.state/recovery/backup.json`, `volumesnapshot.json`, `volumesnapshotcontent.json`, `volumesnapshotclass.json`, `pvc.json`, `pv.json`, `fixture.json`, `cluster.json`, and `baseline-finalize-audit.json`. Together they preserve Backup labels/LSNs, the paired-snapshot identities and source lineage, the separate-WAL layout, source system identifier, image/version, and successful seed evidence. CNPG also recommends preserving `VolumeSnapshot` definitions because `VolumeSnapshotContent` alone omits labels and annotations needed to reconstruct the backup relationship.

The reusable `export_cnpg_wal.py` and focused tests are in this directory. The original 50/100 preparation script records the Backup name and paired DATA/WAL VolumeSnapshot names in `.state/prepare.json`, but it does not save the Kubernetes Backup/VolumeSnapshot objects or a finalization audit; its temporary captures are removed at exit. Once a stack has a completed `prepare-process.json`, `prepare.json`, and the coordinator's completed hash-bound `preflight/staging-retirement.json`, first run `python3 recovery/backup-retention-review/export_cnpg_wal.py STACK --capture-evidence`. This performs bounded read-only queries through that stack's isolated kubeconfig plus two exact ARM snapshot reads, verifies the namespace/Cluster/Backup owner and names, VolumeSnapshot/content/class bindings, source disks, and the owned Blob host/container/prefix/server from the Cluster's saved last-applied configuration, then writes private evidence under `recovery/backup-retention-review/evidence/STACK/` without touching `.state`.

After capture, run `python3 recovery/backup-retention-review/export_cnpg_wal.py STACK --plan-only` to review the exact WAL range, followed by `python3 recovery/backup-retention-review/export_cnpg_wal.py STACK` to export it before cleanup. The exporter verifies the captured evidence file hashes and preparation/process/script/source-stage receipts again, then exports only the start-through-end WAL segments and matching backup-history/timeline objects. It fails closed if an object is missing, ambiguous, compressed by an unsupported codec, mismatched, or incomplete. The 50/100 preparations are still running, so neither capture nor export has been attempted for those stacks.

Validation for the exporter: `python3 -m unittest -v recovery/backup-retention-review/test_export_cnpg_wal.py` passes ten focused WAL, history, and original-prepare-schema/hash-binding tests. A local regression also reloaded the unchanged baseline backup/snapshot lineage successfully. The baseline plan-only check passed before the export.

## Official references

- [CloudNativePG Recovery documentation](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/docs/src/recovery.md) — snapshot recovery requires access to a WAL archive to reapply changes and finalize; a separate WAL PVC also requires its paired snapshot.
- [CloudNativePG API reference](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/docs/src/cloudnative-pg.v1.md) — `waitForArchive` defaults to true and warns that WAL needed to make an online backup consistent may be missing otherwise.
- [PostgreSQL 16: `pg_backup_stop`](https://www.postgresql.org/docs/16/functions-admin.html) — with `wait_for_archive=true`, backup stop waits for required WAL archival and creates a backup-history file in the archive.
- [PostgreSQL 16: Continuous archiving](https://www.postgresql.org/docs/16/continuous-archiving.html) — recovery of an online backup requires the WAL sequence from backup start, and documents the backup-history file's role.
- [CloudNativePG 1.25: Backup on volume snapshots](https://cloudnative-pg.io/docs/1.25/backup_volumesnapshot/) — CNPG uses `waitForArchive` for online snapshots and recommends preserving `VolumeSnapshot` definitions. The deployed 1.30.1 recovery guidance above is the basis for the archive export recommendation.
