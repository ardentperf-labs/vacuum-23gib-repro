The snapshot responses do not expose a logical sector size for these Standard snapshots. The manifests therefore mark 512 bytes as a lineage inference: the keeper and intermediate stage are Standard managed disks created without a sector-size override. Azure's documented migration path requires 512-byte logical sectors for Standard-to-Premium SSD v2 conversion and requires an incremental source snapshot. The restore path must set the Premium v2 disk sector size explicitly to 512 and verify that value on the resulting Azure disk before admitting the run. `01-provision.sh` already sets `LogicalSectorSize: "512"` in the Premium v2 StorageClass and verifies it. The upstream Azure Disk CSI v1.35.0 code forwards that StorageClass value into disk creation and persists it in `creationData`; the published parameter table still describes it as Ultra-only, so the live disk property remains the definitive check. See the [v1.35.0 disk create path](https://github.com/kubernetes-sigs/azuredisk-csi-driver/blob/v1.35.0/pkg/azuredisk/controllerserver.go) and [sector property handling](https://github.com/kubernetes-sigs/azuredisk-csi-driver/blob/v1.35.0/pkg/azureutils/azure_disk_utils.go), along with Microsoft's [snapshot-based disk conversion instructions](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-convert-types?tabs=azure-powershell) and [Premium SSD v2 deployment limits and settings](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-deploy-premium-v2?tabs=azure-cli).

## Recommended source path

Use the region-matched incremental sources above; do not create another regional staging disk or use the nonincremental `vacuum-copy-16244c2c` restore copy. The new stack's `02-prepare.sh` creates one `CopyStart`, incremental Standard snapshot from the allowlisted external source into that stack's own retained-snapshot resource group, waits for completion, and imports only that owned copy as the CSI source. This is the shortest path that keeps the external snapshots and their locks untouched while giving the AKS control-plane identity access only to snapshots owned by that stack. No RBAC grant should be created at either external source snapshot scope.

Each stack's `01-provision.sh` grants its AKS control-plane identity `Disk Snapshot Contributor` on its own token-tagged retained-snapshot group. That assignment is stack-owned and should be recorded with the group's retained state. A previous test proved that deleting a role assignment at a directly locked snapshot scope returns Azure `ScopeLocked`; its helper temporarily removed and restored locks. Do not repeat that operation against any existing source lock. If later cleanup cannot remove a stack-owned assignment while preserving every snapshot, record the assignment ID and deleted principal as residual state.

Azure CSI restore from a `VolumeSnapshot` is the path currently implemented. If that path fails its output 512-byte sector check, stop before running VACUUM and resolve the CSI sector-size behavior; do not relax the check. A direct managed-disk restore with an explicit sector size plus static PV would avoid ambiguity, but requires a larger CNPG bootstrap change and is not the minimal path.

## Baseline comparability

All three arms should start from the 512-GiB keeper lineage and run the same fixture rebuild. Do not use the already prepared 23-GiB DATA/WAL pair from the `prefetch-off-fpw-off` experiment for one arm: it restores an existing 23-GiB fixture after GUC changes, so it would have a different fixture/preparation/cache history. The original baseline `02-prepare.sh` and `experiments/20261005-four/baseline/02-prepare.sh` are byte-identical (SHA-256 `29ef390fdbc3418d529c755fbca34b5f2718e76f03e9b3726c6023fa75379b4c`). Its 100-GiB counterpart uses the same fixture algorithm and keeper system identifier.

The reproducible fixture operation copies a bounded indexed prefix of the keeper's 1536-byte incompressible rows, duplicates each row to the target heap, builds the ID index, deletes half the rows, and checkpoints. It restores baseline PostgreSQL settings and later separates PGDATA and WAL into four 512-GiB volumes across primary and replica. The prior 23-GiB state records a `24696061952`-byte heap; the prior 100-GiB state records `107374182400` bytes and table size `108872679424` bytes. The planned 50-GiB arm should use the same script and record the actual heap, table size, tuple counts, and keeper system identifier in its prepare metadata.

The earlier 100-GiB HDD validation also made a separate cold DATA/WAL backup and restarted PostgreSQL only for that arm. Do not carry that special cold-snapshot path into one Premium v2 size. The current Premium v2 script applies the same final image/restart, archive-cache-clear, checkpoint/replay, and ready-state boundary to each arm; retain that common sequence and its evidence before measurement. The test should start only after every restored Premium v2 disk reports fully hydrated, the same 3000 IOPS/125 MB/s settings, zone 1, and a 512-byte logical sector.

Because the agreed placement puts 23 and 100 GiB in East US but 50 GiB in West US 3, the size series is not a region-controlled comparison. Label region and VM configuration in outputs; only compare 23 against 100 GiB as a same-region size contrast. Treat 50 GiB as a separate regional observation unless a same-region placement becomes available.

## Framework audit notes

`framework/02-prepare.sh` now uses `PremiumV2_LRS` for its data/WAL StorageClass and verifies each actual disk's SKU, capacity, 3000 IOPS, 125 MB/s, selected zone, 512-byte sector size, attachment, and full hydration before producing prepare metadata. Its own early StorageClass assertion at line 102 omits `LogicalSectorSize`; add that check so the script fails before it starts snapshot restore if someone supplies a stale or altered class. `03-test.py` also checks the actual Azure disk sector but its StorageClass assertion omits this parameter. Remaining `Standard_LRS` uses are intentional for the WAL archive storage account, incremental source-copy snapshots, and CNPG volume-snapshot metadata; do not replace them as though they were the four workload disks. It still needs the selected region-specific source manifest passed in explicitly (`SOURCE_MANIFEST`) and the immutable source ID must match it.

`framework/03-test.py` verifies exactly two ready primary/replica pods on separate nodes in the selected zone; four distinct P2 DATA/WAL disks; fixture/system ID and PostgreSQL settings; no active unexpected Jobs (only completed CNPG snapshot-recovery Jobs are accepted); VACUUM start and successful completion markers; and replica replay through the completion flush LSN. It does not launch a client workload (`clientCreated: false`). Its SQL guard counts only `app` user client-backend sessions, so it will detect the expected application account but would not detect a session under a different database user. For a strict no-client-workload claim, preserve the no-client-job gate and report the wider `pg_stat_activity` client-backend inventory alongside this existing guard. Observer `psql` calls and the one owned VACUUM connection are instrumentation, not workload.
