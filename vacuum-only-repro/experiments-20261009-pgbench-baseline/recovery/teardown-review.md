# Teardown and recovery review

Scope reviewed: `run/01-provision.sh`, `run/04-teardown.sh`, and the corresponding owned-watcher cleanup pattern in the immutable `experiments-20261007-premium-v2` archive. This review made no Azure calls and changed no run scripts.

`04-teardown.sh` has strong snapshot retention guards. It verifies the stack-owned retained-snapshot resource group and its `CanNotDelete` lock, inventories every snapshot and installs a missing per-snapshot lock, writes a retention receipt, refuses snapshots in the node/test groups, and keeps source disks while a copy operation is nonterminal. Its role cleanup targets the saved Disk Snapshot Contributor assignment ID only after confirming its exact principal, scope, and role. It leaves a `ScopeLocked` assignment recorded as residual rather than removing a snapshot lock.

Three integration gaps remain before the teardown can claim full cleanup:

1. `01-provision.sh` can create the stack-owned Network Watcher when the regional baseline is empty, and records its exact ID, tags, ETag, and resource group. `04-teardown.sh` does not remove that watcher or its group. The new [`cleanup-owned-watcher.py`](cleanup-owned-watcher.py) checks that identity and its regional baseline, requires an empty dedicated group, uses the saved ETag as an `If-Match` condition, deletes only the exact watcher ID, waits for disappearance, and deletes the empty tagged group. It defaults to dry-run; mutation also requires `--all-stacks-gone`, because the watcher may be shared after another stack adopts it. It never deletes locks or other regional watchers.

2. Paired restore needs to persist source-reader grant intent before any Azure grant creation. [`cleanup-source-readers.py`](cleanup-source-readers.py) follows the current `state.sourceSnapshotReaderAssignments` shape and validates each client-generated assignment ID, exact source scope, principal, Reader role, and source snapshot `uniqueId` pinned in `run/source-manifest.json` (DATA and paired WAL). The restore path must confirm that the new AKS principal has no existing direct grants at either source scope before its first grant, then persist an intent row before calling Azure. Cleanup verifies both source snapshot UIDs and every exact-scope assignment before deleting anything; it issues only `role assignment delete --ids <saved-id>`. Grants for other principals are preserved. An unrecorded assignment for this stack principal, changed role/principal/scope, unexpected snapshot ID, or changed source UID stops cleanup. A lock-protected assignment is reported as residual and never causes a snapshot lock to be removed.

3. The test resource group contains the WAL Blob account/container. `04-teardown.sh` verifies that the group is stack-owned and has no snapshots, then deletes it, but does not prove required WAL exports have been copied and verified locally. Integrate a local WAL-retention/export guard and a fresh all-snapshot retention audit before deleting the test group. The old bundle's `recovery/wal-cleanup-guard/verify_wal_retention.py` is the proven sequence: verify local export receipts/files and a current complete snapshot audit before any stack teardown. Its receipt schema and 3-stack constants should be adapted for this single 2026-10-09 run, not copied unchanged.

The old `post-measurement-cleanup-v2.py` also provides the watcher order: wait for every experiment and node resource group to be absent, inventory the dedicated watcher group, delete only the exact recorded watcher, poll until absent, recheck that the group is empty, and then delete the group. Its first cleanup attempt refused a still-nonempty watcher group and a later retry succeeded after the resource inventory settled. The new helper polls for that exact-resource-list lag and still refuses unknown children. The old cleanup used a separately fetched ARM bearer token; these new helpers use only the configured `az` CLI executable so the credential broker remains in the path and no token is read or printed.

The watcher helper must run after the WAL guard, retained-snapshot audit, and all stack teardown receipts have passed. The source-reader helper should run while the state and paired-restore evidence still exist, before deleting local runtime state; retry any lock-protected residual only after the AKS principal is gone. Neither helper targets snapshots, Blob objects, or unrelated assignments.

## Offline validation

Each helper has a built-in `--self-test` covering wrong owner tokens, unexpected snapshots/resources, changed watcher ETags or role IDs, unknown direct role assignments, and source snapshot replacement. These tests are local-only and do not call Azure.
