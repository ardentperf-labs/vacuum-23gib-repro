# PostgreSQL 16 recovery-prefetch context

This note interprets the prefetch-off run using PostgreSQL 16.15 documentation and source. It does not change the measured values in [REPORT.md](REPORT.md).

## Behavior supported by PostgreSQL documentation and code

PostgreSQL 16 documents `recovery_prefetch` as a recovery-time setting. `try` (the default) attempts to prefetch WAL-referenced blocks that are not already in shared buffers, subject to platform support; `off` disables that attempt. The documentation says prefetching can reduce recovery I/O wait for some workloads, and that WAL lookahead and I/O concurrency constrain it ([PostgreSQL 16 WAL configuration](https://www.postgresql.org/docs/16/runtime-config-wal.html#GUC-RECOVERY-PREFETCH)). The PostgreSQL 16.15 prefetcher source describes looking ahead in WAL and initiating I/O for blocks expected to be accessed soon when they are absent from the buffer pool. It currently considers only the main fork ([PostgreSQL 16.15 `xlogprefetcher.c`](https://github.com/postgres/postgres/blob/REL_16_15/src/backend/access/transam/xlogprefetcher.c)).

The same source explicitly skips prefetch for a WAL block reference carrying a full-page image, increments `skip_fpw`, and returns without scheduling that prefetch. The redo code handles an applicable full-page image by obtaining a zero-and-lock buffer and restoring the image; it returns `BLK_RESTORED`. That path does not fetch the prior on-disk page contents through the ordinary page-read path ([PostgreSQL 16.15 `xlogprefetcher.c`](https://github.com/postgres/postgres/blob/REL_16_15/src/backend/access/transam/xlogprefetcher.c), [PostgreSQL 16.15 `xlogutils.c`](https://github.com/postgres/postgres/blob/REL_16_15/src/backend/access/transam/xlogutils.c)). Thus an FPI count is not a count of standby data-disk reads, and the 6,071,356 FPIs observed here do not imply that many device reads. WAL records can also refer to blocks without requiring a prefetch, for the explicit reasons represented by the other recovery-prefetch counters ([`pg_stat_recovery_prefetch` documentation](https://www.postgresql.org/docs/16/monitoring-stats.html#MONITORING-PG-STAT-RECOVERY-PREFETCH)).

## What this experiment establishes

In this run, the standby's live setting was `recovery_prefetch=off`; the primary remained at `try`. Over VACUUM plus catch-up, the measured standby DATA reads were about 14.4 MB, compared with about 48.7 GB in the original `try` run. The WAL marker deltas were effectively the same: 36,932,318,738 bytes, 15,115,437 records, and 6,071,356 FPIs. `pg_stat_recovery_prefetch` cumulative counter deltas were zero on both roles in this run.

These observations are consistent with the two runs having very different standby DATA-read activity under different prefetch settings, but they do not establish that `recovery_prefetch` caused the difference. The `off` run was in West US 3 and the original was in East US, so region is a confound; there is also no contemporaneous same-region on/off pair. The zero counter delta is consistent with this standby setting and is not a measurement of how many reads `try` would have prefetched in the other run. The observed 14.4 MB is a device-counter measurement, not a direct count of PostgreSQL page-read calls, and the run's approximately 336 standby DATA reads make its read-await statistic sparse rather than representative of sustained replay reads.

An independent recount verified the DATA/WAL PV, mount and LUN mappings across every sample, found monotonic device counters, and reproduced the approximately 336-read exact measurement window from raw `diskstats` deltas. See the [independent raw-count audit](independent-prefetch-read-count-audit.json) and [root recount](root-prefetch-read-count-recheck.json).

## Reading the FPI count carefully

`full_page_writes=on` records a full page image on a page's first modification after a checkpoint to permit restoration from a potentially partial page write; this increases WAL volume ([PostgreSQL 16 `full_page_writes` documentation](https://www.postgresql.org/docs/16/runtime-config-wal.html#GUC-FULL-PAGE-WRITES)). In replay, an applicable image can supply the page contents without first reading the old page from disk. Other WAL block references can still require ordinary reads, and device counters also reflect PostgreSQL and operating-system caching. So neither the total WAL record count nor the FPI count alone predicts standby DATA IOPS. The code documents a plausible way recovery can avoid reads for records carrying applicable FPIs, but this experiment did not measure the fraction of replayed records taking that path or isolate its contribution to device I/O.
