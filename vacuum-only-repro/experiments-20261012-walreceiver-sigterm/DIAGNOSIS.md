# Diagnosis before teardown

This was an invalid, user-stopped pilot because inherited preparation removed the required archive configuration. Both VACUUMs exited successfully, both clients stopped gracefully, and the final native logs reconcile exactly with client summaries and server-side committed-update counters: 40,627 treatment transactions and 40,622 control transactions, with zero failures. Both observation windows ended after about 7,091 seconds, below the 8,400-second minimum, and replay catch-up was not completed. The >2-hour outcome was not evaluated; this is not a negative result from a completed two-hour test.

During the observed treatment interval, the client fixture counter stopped advancing for approximately 36 minutes 46 seconds after the replica walreceiver received SIGTERM. All ten measured writers were repeatedly observed waiting on synchronous replication. The primary sender returned first in `catchup/potential`, then reached `streaming/quorum` at 02:33:38.207 UTC. The first native transaction completion falls inside the roughly one-second sampled transition bracket; fixture counter progress resumed about half a second after the first collector-captured quorum sample. At that point the replica had flushed the primary’s WAL but remained roughly 22.8 GiB behind in replay. With `synchronous_commit=on`, remote flush is the relevant acknowledgement; replay catch-up is not required. The detailed diagnosis preserves sample gaps and final log hashes.

Neither live cluster has an object-storage archive backend configured. The inherited snapshot preparation explicitly removed backup and external archive references after the matched local DATA/WAL snapshot restore passed its fixture checks: [`02-prepare.sh`](shared/02-prepare.sh) clears `spec.bootstrap`, `spec.backup`, and `spec.externalClusters`, then verifies those references are absent before finalizing the replica. The pinned source pair also states that external WAL archive recovery was not required. PostgreSQL still has CNPG’s generic `manager wal-restore` helper configured, so `RestoreCommand` waits can occur without an object-storage request. The installed CNPG v1.30.1 helper skips archive retrieval when no source is configured. Its archive helper can likewise return success without uploading WAL, so successful `pg_stat_archiver` counters do not establish cloud uploads. This preparation mismatch prevented these runs from testing the expected object-storage recovery path. Captured logs show no object-storage fetch or fetch error. The future-timeline-history refusal is separate from archive lookup. The per-lane [treatment archive diagnosis](sigterm/results/diagnosis/public/archive-backend-diagnosis.json) and [control archive diagnosis](control/results/diagnosis/public/archive-backend-diagnosis.json) include safe runtime classifiers, configuration references, and their checksummed capture receipts.

The observed treatment interval had a 2,206.031-second native completion gap; the corresponding post-gap transaction execution time was 2,205.848 seconds. This did not reach the hoped-for two-hour interval, and the >2-hour result remains unevaluated because the pilot ended early. The treatment signal was 73.729 seconds late after the first PostgreSQL termination function returned false. These deviations and the user-stop receipt remain in the raw evidence. A clean repeat requires working WAL archiving on both stacks and independently verified archive uploads before measurement.

The [treatment timeline](sigterm/results/diagnosis/write-resumption-diagnosis.md) records exact observations and sample gaps. Each lane’s `results/diagnosis/public/` contains runtime settings, archive-source references, WAL inventory, filtered PostgreSQL/CNPG events and a checksummed capture manifest. Full logs and raw configuration are retained privately outside the Git checkout. The final native client evidence is now reconciled. Teardown and archive/publishing decisions remain with the root controller.

Behavior references: [CNPG v1.30.1 restore helper](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/internal/cmd/manager/walrestore/cmd.go), [CNPG v1.30.1 archive helper](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.1/pkg/management/postgres/archiver/archiver.go), [PostgreSQL synchronous commit](https://www.postgresql.org/docs/16/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT), and [PostgreSQL sender quorum selection](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/replication/syncrep.c).

For a clean archive-enabled repeat, retain the local paired-snapshot bootstrap, then configure a dedicated Azure Blob container and unique per-run prefix after fixture validation. A low-cost option is one same-region Standard StorageV2 account with LRS replication, a pre-created Hot-tier container, and a separate prefix for each lane. Keep the CNPG archive references in the measurement Cluster. The in-tree `spec.backup.barmanObjectStore` path requires an image containing Barman Cloud; the `16.15-standard` image does not include those binaries. Use the matching `16.15-system` image for the in-tree path, or retain the standard image and install the CNPG Barman Cloud plugin with its sidecar. The in-tree path still works in CNPG 1.30.1 but is deprecated; the plugin is the forward path. Store Azure credential references in a Kubernetes Secret and keep Secret values out of artifacts. Before starting VACUUM, force a WAL segment switch and require matching byte count and SHA-256 for the local closed WAL segment, its Blob download, and a `wal-restore` download to a unique temporary path outside `PGDATA`. Preserve archive configuration through replica finalization and capture `pg_stat_archiver`, safe command classifiers, plugin/object-store status, restore logs, and WAL inventory. See the [CNPG 1.30 Azure object-store configuration](https://cloudnative-pg.io/docs/1.30/appendixes/object_stores/), [CNPG 1.30 Barman configuration](https://cloudnative-pg.io/docs/1.30/appendixes/backup_barmanobjectstore/), and [official PostgreSQL container image variants](https://github.com/cloudnative-pg/postgres-containers).
